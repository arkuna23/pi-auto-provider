# Configuration

`pi-auto-provider` discovers models for custom providers listed in Pi's
`auto-provider.json`. Provider connection and authentication settings are separate from
the generated model catalog in `models.json`.

## Breaking change

This release intentionally changes the configuration source:

- Automatic providers are read only from `auto-provider.json`.
- Provider entries in `models.json` are ignored for automatic-provider selection.
- Existing providers must be recreated in `auto-provider.json`; no automatic migration is performed.
- The plugin-owned `auto-models.cache.json`, `auto-models.json`, and project
  `.pi/auto-models.json` paths are obsolete and are removed best-effort on startup
  or refresh.
- Pi-owned `models.json` and `models-store.json` are retained.

A provider that exists only in `models.json` therefore stops being registered after
this change.

## Files

| File | Purpose | Owner |
|---|---|---|
| `~/.pi/agent/auto-provider.json` | Authoritative automatic-provider connection and auth settings. | You |
| `~/.pi/agent/models.json` | Pi provider catalog, including static model definitions generated by this extension. | Pi and this extension's target model arrays |
| `~/.pi/agent/models-store.json` | Pi's separate refreshed-model runtime cache. | Pi |
| `~/.pi/agent/auto-models.cache.json` | Obsolete parameter cache; removed best-effort. | Legacy plugin output |
| `~/.pi/agent/auto-models.json` | Obsolete user override file; removed best-effort. | Legacy plugin input |
| `.pi/auto-models.json` | Obsolete trusted project override file; removed best-effort. | Legacy plugin input |

The agent directory is controlled by Pi and can be relocated with
`PI_CODING_AGENT_DIR`.

## Provider configuration

Add providers under the top-level `providers` object:

```jsonc
// ~/.pi/agent/auto-provider.json
{
  "providers": {
      "my-proxy": {
        "baseUrl": "http://127.0.0.1:8080",
        "api": "openai-completions",
        "apiKey": "$MY_PROXY_KEY",
        "authHeader": true,
        "headers": {
          "X-Tenant": "$MY_TENANT"
        },
        "compat": {
          "supportsStore": false,
          "maxTokensField": "max_tokens"
        },
        "name": "My proxy"
      }
    }
  }
}
```

The standalone file is parsed as JSONC, so comments and trailing commas are allowed.
Unrelated Pi settings remain untouched.

### Provider fields

| Field | Required | Description |
|---|---|---|
| `baseUrl` | Yes | HTTP(S) endpoint. The extension appends `/v1/models`, or `/models` when the path already ends in `/v1`. |
| `api` | Yes | Registered Pi API implementation, such as `openai-completions` or `openai-responses`. |
| `apiKey` | No | Literal, environment interpolation, or leading command value. Empty/keyless providers are supported. |
| `authHeader` | No | When `true`, send `Authorization: Bearer <resolved key>`. |
| `headers` | No | Additional string-valued request headers. Values use the same resolution syntax as `apiKey`. |
| `compat` | No | Compatibility defaults applied to generated model definitions. |
| `name` | No | Display name shown for the provider. |

Built-in Pi provider ids are not registered by this extension. A custom entry with
missing or invalid routing information is reported as a configuration error and is
skipped. Credential values are never included in those diagnostics.

### Value resolution

Pi resolves configured credential values using these forms:

- `$ENV_VAR` and `${ENV_VAR}` resolve environment variables, including inside larger strings.
- `!command` at the beginning runs a shell command and uses trimmed stdout.
- `$$` emits a literal `$` and `$!` emits a literal `!`.
- Other strings are literal values.

The extension passes references through to Pi's provider registration and resolves
request headers only for the outgoing request. Resolved credentials are not written
to `models.json`, `models-store.json`, refresh summaries, or other plugin artifacts.

## Models catalog persistence

On a successful online refresh, the extension:

1. Queries the provider's `/v1/models` endpoint.
2. Enriches model ids with built-in or `models.dev` metadata when available.
3. Replaces only that provider's `models` array in `models.json`.
4. Removes stale entries no longer returned by the provider.
5. Publishes the runtime models to Pi's `models-store.json` as usual.

Generated model definitions are compact. Shared provider metadata is written once at the
Provider level, while each model keeps only its own stable restore metadata:

- Provider-level `api`, `baseUrl`, and configured `compat` values
- Model-level `id` and non-default `name`
- reasoning and thinking-level capabilities when enabled
- non-default input modalities
- non-zero costs and tiers
- non-default context and output limits

Default model values such as text-only input, non-reasoning, zero costs, a 128000
context window, and a 16384 output limit are omitted and restored by the extension.
The generated entries omit internal `provider` identity and all credential fields.
Provider-level legacy fields that are unrelated to the generated `models` array may
remain physically in `models.json`; they are not consumed as automatic-provider
configuration. Standalone-file registration wins at runtime for connection,
authentication, headers, compatibility, API, endpoint, and naming values.

The catalog update uses JSONC-aware structured edits, a lock, and atomic replacement.
Unrelated providers and unrelated fields on the target provider are preserved. Read,
parse, validation, lock, or rename failures are surfaced as refresh errors and do not
replace the previous `models.json`.

### `models-store.json` is separate

Pi's `models-store.json` is not the same as the static `models.json` catalog. Pi uses
it for its refreshed runtime snapshot. On session start, the extension keeps the
existing offline restoration behavior by accepting Pi's stored models without a
network request. Neither Pi-owned file is deleted by legacy cleanup.

## Runtime precedence

For an automatic provider registered by this extension, settings values are the
runtime authority even when stale fields remain in the corresponding `models.json`
provider entry:

1. Settings-backed extension registration supplies provider name, API, endpoint, auth,
   headers, auth-header behavior, compatibility, and refresh callback.
2. The generated model array supplies static model metadata and restore definitions.
3. Pi's `models-store.json` supplies the separate offline runtime snapshot.

Do not put automatic-provider credentials in `models.json`. Existing values there are
ignored by this extension and may remain only because unrelated provider fields are
preserved during catalog updates.

## Refreshing

- **Startup:** a session-start offline refresh restores the model list from Pi's
  `models-store.json`, or from generated static definitions in `models.json` when no
  store entry exists.
- **Online:** run `/refresh-models` to query providers and update both the static
  catalog and Pi's runtime store.
- **Failure:** the previous static catalog remains intact; the error is shown in the
  refresh result.

Legacy cleanup is limited to these exact paths:

- agent `auto-models.cache.json`
- agent `auto-models.json`
- current project `.pi/auto-models.json`

Cleanup is best-effort and reports filesystem diagnostics without touching
`models.json` or `models-store.json`.
